1.3 Research question: what blocks low-latency, natural, real-time Speech-LLM conversation?

Reading the two designs against each other, I see five limitations. Each is tied to a number or design choice in the reports.

  1. The latency floor is set by the representation, not the LLM. Moshi's 160 ms is two 80 ms frames; going lower means a higher frame rate, which multiplies sequence length. A 12.5 Hz × 8-codebook stream is 100 audio tokens per second against roughly 3–4 text tokens per second for the same content, so the backbone spends ~25–30× more steps per second of content than a text LLM. The Depth Transformer and MTP module exist to hide this cost.
  2. Full-duplex and strong reasoning have not been combined. Moshi gets ~200 ms and natural overlap, but it is a 7B model with a 4-minute context trained mostly on English. Qwen3-Omni has a far stronger Thinker but a turn-based interface, so the system must decide when the user has finished before it can commit to answering. Any silence timeout used for that decision adds directly to response time and cannot distinguish a thinking pause from a finished turn.
  3. Latency is not constant under load. Qwen3-Omni's own table shows first-packet latency rising from 234 ms to 1172 ms between 1 and 6 concurrent streams, driven by Thinker and Talker time-to-first-token (88 → 673 ms and 57 → 376 ms). Real-time behaviour therefore depends on serving, not only architecture.
  4. Speech tokens carry less reasoning ability than text. Moshi needed the inner-monologue text stream because predicting audio tokens directly gave poorer linguistic quality (their ablation ranks it among the most critical design choices). Qwen3-Omni likewise routes everything through a text-producing Thinker (inference: plausibly for the same reason; the report does not say). Either way, the system speaks only as fast as text plans ahead, and prosody that depends on future content (emphasis, question intonation) must be guessed.
  5. Coverage of languages that matter here. AuT's pre-training mix is 80% Chinese/English and 10% other-language ASR; the 19 supported speech-input languages contain no Hindi or Tamil (Urdu is the only Indic-region language). Moshi is English-focused. My Task 2 results show the practical consequence: with a small multilingual stack, Hindi is limited by ASR errors and Tamil by the language model's comprehension, and both feed confident wrong answers.

1.4 Proposed improvement: Speculative Think-while-Listening (SpecTL)

Idea. Keep a strong turn-based Thinker–Talker (limitations 2 and 4) but remove the silence-timeout wait. A light head on the 12.5 Hz encoder states predicts the probability that the user's turn is ending, using semantic and prosodic cues. While the user is still speaking the Thinker drafts a response behind a KV-cache snapshot. When the head's probability crosses an upper threshold the draft is committed and the Talker starts; if the user continues, the draft is discarded and the cache is rolled back. This is speculative decoding applied to turn-taking rather than to tokens.

Hypotheses. H1: a learned turn-end head with a latency-aware loss gives lower response latency than a fixed 500–700 ms silence timeout at the same false-cut rate. H2: the wasted Thinker compute from rollbacks is small enough (<15% of drafted tokens) to be paid for by the saved wait. H3: an encoder trained on Indic data with the same head transfers poorly from English turn-end cues (Indic languages differ in final particles and pause structure), so an Indic-balanced head is needed.

Experiment design. (a) Data: two-channel dialogue with word-aligned turn ends; English (Fisher-like) plus Hindi/Tamil and code-mixed conversational audio. (b) Baselines: fixed-silence VAD, Moshi-style implicit turn-taking. (c) Metrics: response onset minus true turn end (ms), false-cut rate, wasted draft tokens, and answer quality (judge score) so speed is not bought with worse answers. (d) Ablations: head inputs (semantic only, prosody only, both), loss weight λ, threshold pair, Indic vs English-only training. Status: this is a proposal; I have not run it.
